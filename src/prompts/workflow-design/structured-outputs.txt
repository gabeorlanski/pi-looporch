# Structured outputs

Treat a schema as a minimal **transport contract**. Put task semantics, evidence requirements, and completion criteria in the prompt; the schema carries only fields consumed by workflow code.

- Add a field only when a downstream consumer reads it. Prefer a decision enum or boolean, stable IDs, counts, and artifact paths.
- Keep the object shallow, require every consumed field, and set `additionalProperties: false`.
- Use short domain names. Descriptions belong only on fields whose meaning or allowed value cannot be made clear by the name, type, enum, and task packet.
- Add length or item bounds only for real downstream limits.
- Keep reports, reasoning, evidence collections, diffs, and transcripts in files; return their paths.
- For large sets, return a bounded manifest or selector, then expand only selected IDs in a later stage.
- Runtime fields `message`, `name`, `steps`, and `usage` are reserved. A schema-enabled child returns the authored fields plus runtime `message: null`, `name`, `steps`, and `usage`.

`agent({ template, values }, { schema })` exposes the authored schema unchanged as the terminal `StructuredOutput` tool parameters. The runtime does not repeat that JSON in the task prompt. The child must call the tool once to finish.

`LLM(prompt, { schema, retries? })` has no tool, so its system instruction includes the schema. It retries malformed or nonconforming JSON up to three times by default.

```js
const schema = {
  type: "object",
  properties: {
    verdict: { type: "string", enum: ["pass", "fail"] },
    reportPath: { type: "string" },
  },
  required: ["verdict", "reportPath"],
  additionalProperties: false,
};
```
