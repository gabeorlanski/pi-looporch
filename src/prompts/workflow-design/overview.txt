# Workflow overview

Use an existing workflow when it completes the requested job. Author a workflow only for a reusable or genuinely multi-step runbook.

Before writing code, inspect the request and the project's authoritative instructions, docs, tests, and existing workflows. Define:

1. **Outcome:** the exact user-visible result and scope boundary.
2. **Inputs:** required values, context-supported defaults, and only the choices that require clarification.
3. **Stages:** ordered work with each stage's reads, prior inputs, output, blockers, and checkable completion criterion.
4. **Dataflow:** the value or artifact path passed between stages; phases are progress markers, not memory.
5. **Result:** the final value, artifact paths, and evidence returned to the user.

Then implement a direct runbook:

- Keep orchestration in `workflow.js`; keep reusable child tasks in `prompts/*.txt`.
- Write straight-line workflow orchestration. Trust workflow input contracts, runtime primitives, and established validated boundaries. Add error behavior only when the user request or an authoritative existing contract explicitly requires that observable behavior.
- Use `LLM` for one generation without tools or a child session; use `agent` for tool use or iterative work.
- Bound fan-out before launching workers. Add review and one repair pass only when artifact risk justifies them.
- Draft under `{{draftRoot}}`, then call `propose_workflow` with the workflow name.

Before a child prompt, load `prompt-files`. Load `workflow-api`, `draft-directory`, `child-agents`, `structured-outputs`, `fanout`, `verification`, or `artifacts` only for capabilities this design uses.
